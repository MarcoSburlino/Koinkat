# Current tool contracts

Behavior implemented in the first read/calculation milestone. Tool discovery supplies strict JSON input schemas; unknown input fields are rejected. Every successful result includes `workspaceId`, `observedAt` and `data` in both structured content and text JSON. Errors are marked `isError`.

## Workspace and freshness

The workspace is fixed by CLI `--workspace`; tools cannot choose another workspace. `get_context` returns workspace identity, preferred currency, earliest/latest transaction dates, transaction count, latest transaction update timestamp, last stored bank-sync time and latest cached exchange-rate date. Observation time is not bank-sync time. No call causes an import or rate refresh.

`list_accounts` returns paginated accounts, native balances, converted balances and full-account totals. `list_categories` returns paginated IDs, names, types and parent IDs. Pagination uses `limit` (default 50, maximum 200), `offset` and `hasMore`.

## Transactions and totals

`search_transactions` supports inclusive `startDate`/`endDate`, `accountId`, `categoryId`, `budgetEventId`, `transactionCurrency`, case-insensitive literal `merchant` substring, `type`, `status`, `needsReview`, `recurring`, and decimal-string `minAmount`/`maxAmount`. Categories match the exact assigned category ID, not descendants. Amount bounds compare original positive transaction amounts in their original currency; use `transactionCurrency` when comparing amounts. No wildcard or executable SQL input is accepted. Results sort by date descending, then ID ascending.

Search includes pending rows, transfers and repayments unless filtered. `get_transaction` returns the selected transaction plus linked parent/children and paired transfer rows, each list capped at 200 with explicit truncation flags. It also returns existing external reimbursements. It does not retrieve bank credentials or bank identifiers.

`summarize_transactions` accepts those filters plus output `currency` (default workspace preferred), `groupBy` (`none`, `category`, `merchant`, `account`, `month`, `week`) and group pagination. `category` groups by the directly assigned category, not its parent macro. Weeks use their Monday date. Monthly keys are `YYYY-MM`.

Summaries always use booked income/expense rows, excluding repayments, native transfers and confirmed transfer pairs. Split parents use stored signed net cost. Gross amounts remain available from search/detail. Totals cover all matching eligible rows, independent of group pagination. `matchingCount`, `includedCount`, `excludedCount` and `convertedCount` explain what contributed. Income minus expenses is `net`; it is not a reconstructed account balance.

Account and transaction summaries use latest cached rates, matching Koinkat's display-time reporting. Conversion rounds each converted amount to cents and does not quantize the cross rate first. Missing conversions are excluded, with `complete: false` and their currencies disclosed. These are partial totals, not zero-cost transactions. Account currencies and cached rate keys are expected in Koinkat's normalized formats.

## Budgets and events

`get_budgets` requires `year`. It returns recurring budgets and already persisted periods for that year, plus **all** workspace events including undated and expired events. Missing periods are not generated by a read call.

Regular period spending includes booked budgeted expenses without event links inside the period. Active events folded into the period's start month contribute their budgeted linked spending regardless of transaction date, and their limits increase the effective period limit. Each expense is counted once. Event spending itself counts all eligible linked expenses even when not included in the recurring budget. Both apply split/repayment/transfer rules.

Historical conversion uses an exact-date cached rate, otherwise nearest-earlier cached rate, otherwise the latest cached rate. This matches Koinkat's offline fallback behavior. Unlike the app's online behavior, MCP never fetches missing historical rates. `usedRateDates` and `datesUsingFallbackRates` disclose fallback use; each event/period discloses missing currencies and completeness.

## Recurring and shared expenses

`list_recurring_expenses` accepts `status` (`active` default, `paused`, `ended`) and pagination; it returns confirmed series, cadence, expected amount/currency and last/next charge dates. It does not run recurring discovery or infer a missed-charge status.

`list_split_expenses` accepts `status` (`open` default, `settled`, `all`) and pagination. Gross, net and reimbursed figures are in the account currency. Stored split net values are not recomputed. An open split does not encode a predetermined personal share or how much a particular friend owes.

## Decimal calculations

`calculate` takes `operation`, up to 100 `operands` of `{value: decimal string, currency?: ISO code}`, and `decimalPlaces` (default 2, maximum 12). Plain decimal inputs are bounded to 40 integer and 20 fractional digits; exponential notation and executable expressions are rejected.

- `sum`, `average`: one or more operands with matching currency labels, or all unitless.
- `subtract`: two or more operands, evaluated left to right, with matching units.
- `multiply`: exactly two operands, at most one with a currency label.
- `divide`: exactly two; divisor may be unitless or use the numerator's currency. Dividing equal currencies yields a unitless result.
- `percentage_of`: first divided by second, multiplied by 100; matching input units.
- `percentage_change`: `[old, new]`, `(new - old) / abs(old) * 100`; matching input units.

Division by zero is an error. Output uses a decimal string, unit and explicit half-up rounding. Division uses 40 decimal places of intermediate precision. No currency conversion or persistence occurs inside this tool.

## Bounds

Transaction scans stop at 100,001 rows and reject requests above 100,000 before presenting any result as complete. Narrow filters for larger datasets. Pages and related lists are capped at 200; group and row counts disclose pagination. Maximum serialized response size is 200 KB. Large budget/event responses currently fail with an explicit size error; event filtering/pagination is future work.

All tools currently advertise read-only annotations, backed by a native read-only SQLite connection. No editing tool or arbitrary SQL tool is registered.
